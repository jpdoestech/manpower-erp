## Proposed implementation plan (before code; pending prerequisite)

1. Re-fetch after P1-01 acceptance, record the reviewer/decision and exact accepted
   revision. Verify the chosen implementation base contains it; prefer integrated
   main when available, otherwise explicitly document the accepted stacked base.
   Never merge any prerequisite PR automatically.
2. Finalize ADR-013 and update ARCHITECTURE/SECURITY_RBAC/access matrix. ERP Platform
   is the navigation root, not a legal company. Separate legal company identity,
   head offices, operational branches, client identity and branch engagements.
3. Add reviewed additive Alembic revision after 0003 and organizations models:
   company, effective-dated registration profiles, head office, branch, reusable
   client identity within company, client/branch engagement, contract and site.
   Stable UUIDs, company_id, scope-preserving composite foreign keys and scoped
   uniqueness. Shared clients across authorized branches reference one legal
   identity; no unapproved cross-company directory or global identifier lookup.
4. Preserve dated relationships and history: stable parents once referenced,
   effective-dated replacement relationships, archival rather than physical API
   deletion, RESTRICT foreign keys. Validate date order and parent validity;
   inactive parents cannot acquire new active children. Do not claim preservation
   against future financial tables until those modules define their references.
5. Registration profiles record VAT/Non-VAT/claimed exemption, source/reference,
   validity and review state; they do not derive transaction tax treatment, rates,
   exemption eligibility or final BIR classifications. Retain superseded versions.
6. Bootstrap a single explicit user-to-company organization-admin capability via
   protected operator provisioning with audit; no generic role engine or public
   grant API. Authentication or technical Super Admin alone grants no company
   access. Filter every query/list/search by current grants; reject cross-company
   parent IDs and scope injection. Define future company/HO/branch/client/contract
   scope resolution without implementing P1-03 permissions or financial approval.
7. Implement transactions/services and authenticated typed API with bounded search,
   filters/pagination, validation/conflict errors, CSRF/Origin and safe audit/logging.
   Resolve the ADR-002 runtime-role/RLS boundary before asserting DB isolation:
   non-owner/non-superuser runtime, transaction-local company context, no pool
   leakage, default-deny policies plus composite-FK and service authorization.
   Do not silently claim owner/superuser connections enforce RLS.
8. Add compact labelled company/HO/branch/client/contract/site administration UI,
   explicit company selector from authorized results only, filter/search/page
   controls, archive/status and effective-date validation. Reuse the existing React
   app/API helpers and pinned stack. Do not expose registration details in logs.
9. Run tests/gates, review migration/rollback and update evidence. Commit/push the
   implementation, make the draft PR ready only when appropriate, verify hosted CI.
   Remain REVIEW for required human acceptance; do not start P1-03 or deploy.

## Acceptance tests to implement (none claimed run yet)

- Company A grant cannot read/mutate/list/search/count Company B records; anonymous,
  plain authenticated and ungranted technical-admin requests are denied. Revoked
  grants fail immediately; client company/role headers confer no access.
- A user with explicit grants for A/B sees only those scopes. Branch engagement
  sharing reuses one client identity; no other company's identity details leak.
- Database rejects mixed-company HO/branch/engagement/contract/site references,
  appropriate scoped duplicates, inverted contract dates and invalid versions.
- RLS tested as non-owner/non-superuser: absent/wrong tenant context denied,
  transaction rollback/commit and concurrent pooled requests cannot leak context.
- Inactive/expired parents reject new active relationships; historical references
  survive archival, edits cannot silently move existing contracts/sites to another
  parent, direct deletion of referenced records fails. Date boundary cases covered.
- VAT/Non-VAT/exemption assertions retain evidence/dates/review state without
  automatically authorizing a tax outcome; version replacement retains history.
- Clean/repeat/drift/empty downgrade/re-upgrade on disposable PostgreSQL; populated
  downgrade refuses history loss; existing identity/session/auth audit preserved.
- API validation, safe conflict/error responses, pagination/filter stability,
  CSRF/Origin, bounded search and org audit metadata have automated coverage.
- UI authorized navigation, labelled forms, valid/invalid hierarchy/dates, search,
  filters, pagination, inactive records and safe failure states; prior UI unchanged.
- All existing backend/frontend regressions; Ruff/Biome format/lint, mypy/tsc,
  build, dependency audits, migration CLI, Compose/actionlint/whitespace and hosted CI.
