# CR-002C — Supabase authentication portability (PLAN ONLY)

NOT STARTED. Implementation requires CR-002B acceptance and retained P1-01 human
security gates. No provider SDK, JWT middleware, keys, mapping migration or cloud
service is implemented by this plan. Do not provision/deploy anything automatically.

## Proposed slice and files

1. ADR/AUTH_PROVIDER_STRATEGY: explicit local/Supabase adapters sharing the existing
   authenticated ERP principal. Preserve local Argon2/opaque-session/CSRF path.
   Supabase frontend SDK flow must be real, with strict Origin/redirect handling;
   choose secure token custody before adding code. Prefer a backend session bridge
   using HttpOnly cookies/CSRF so persistent browser bearer-token storage is avoided;
   any SDK memory-only exchange must have a tested refresh/reload design.
2. FastAPI provider verifier: configured issuer/audience, explicit asymmetric
   algorithm allowlist, signature/exp/nbf/sub/session claims and pinned project
   JWKS URL. Bounded fetch/cache, unknown-kid refresh once, rotation/revocation,
   cache purge and unavailable-provider fail-closed tests. Reject alg=none,
   algorithm confusion and attacker-controlled key URLs. No decode-only trust or
   service-role credential in the browser. Legacy shared-secret configuration must
   be explicitly rejected or separately reviewed, never silently treated as JWKS.
3. Additive Alembic mapping: unique (provider, issuer, subject) -> existing internal
   ERP UUID. Never link accounts by email alone or import local password hashes to
   Supabase. Administrator-controlled verified provisioning, inactive-by-default
   mapping and independent account-change approval; no automatic Super Admin grant.
4. Recheck ERP activation and session revocation on protected requests. Provider
   logout alone cannot establish immediate API revocation for an already-issued
   JWT; preserve durable local revocation/session binding and define provider
   disable/password-reset/refresh-reuse synchronization. Audit without credentials.
5. Authentication grants identity only. Company/head-office/branch/client/contract
   authorization remains server-side, deny-by-default, from explicit ERP grants.
   No scopes exist yet; keep company business routes unavailable. Do not implement
   full P1-02/P1-03 RBAC or trust browser claims/headers for company authority.
6. Provider-independent principal and external mapping allow later self-hosted
   OIDC/local authentication without changing financial business logic. Update
   recovery tools to revoke any newly added provider-session capabilities on
   restore. Billing, accounting, tax, Vercel and data transfer remain out of scope.

Likely files: identity provider module, security/service/routes, frontend auth
client/panel, mapping migration, provider/config/rotation/isolation tests,
AUTH_PROVIDER_STRATEGY/SUPABASE_CONFIGURATION and task/status/ADR evidence. Select
compatible pinned libraries only after checking current dependency/security data.

## Acceptance / decisions

Both local and real Supabase test-project login/logout/refresh/expiry/recovery
must pass. Test wrong issuer/audience/signature/algorithm, unknown key/key rotation,
network failure, forged subject, duplicate/unapproved mapping, disabled ERP user,
revoked sessions, refresh replay, provider switch, CSRF and no cross-company
grants. Verify no tokens/passwords/service keys in logs/storage/bundles. Mocked
verification alone cannot claim hosted provider integration. Retain actual PG,
SQLite migration, existing native tools and frontend regression gates.

Before implementation: approve provider configuration, custody/refresh strategy,
technical-admin MFA/step-up, recovery/operator procedures, identity linking and
revocation latency with the security owner. Never infer those approvals from B CI.
Use a disposable test project with backend-only privileged credentials; no real
employee data or production deployment. Record reviewer/date/decision/reference
only when actually supplied.
